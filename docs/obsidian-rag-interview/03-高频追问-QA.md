# 高频追问 Q&A

## Q1：为什么选 Milvus 而不是其他向量库？

Milvus 适合中等到大规模向量检索，支持 IVF_FLAT / HNSW、COSINE 相似度、Docker Compose 一键起 Milvus + etcd + MinIO，能比较自然承接 10 万到 100 万级金融文档。Milvus collection 可以把向量和标量字段放在同一个检索链路里，过滤和排序方便——金融场景下按 `company_id / language / category / published_at` 多维过滤是常态。如果数据量再上量，可以换 HNSW、冷热分层、按时间分区。

## Q2：为什么用 LangGraph？

金融研究类问题通常有多步流程：理解问题、规划检索、检查证据、生成答案。LangGraph 把这些拆成明确节点，每个节点有输入输出和状态流转，方便加条件分支、重试、补检和日志。我在项目里用它把查询分析、路由、检索、评估、多源对比、生成和自反思串起来；Deep Research 进一步拆成 Planner / Retriever / Analyst / Checker / Writer，Checker 发现证据缺口时回到 Retriever 补检。

## Q3：RRF 是什么？为什么适合这里？

RRF 是 Reciprocal Rank Fusion，用排序名次融合多路检索结果。它不依赖不同召回路径的原始分数尺度，只看每条结果在各路中的排名。项目里有语义、关键词、标题三路召回，分数来源和尺度不同，RRF 可以融合成稳定排序。参数 `k=60`，权重 `0.5 / 0.3 / 0.2`，既保留语义泛化能力，也保留实体和标题精确命中能力。

## Q4：为什么 chunk_size 设成 500？

金融文章（研报、新闻、财报摘要）段落通常较短，500 左右 chunk 保留足够上下文，又不会让单向量承载太多主题。太短检索结果缺上下文，引用质量下降；太长命中粒度差，Embedding 成本和噪声增加。实际调优会结合 Precision@5、NDCG 和人工抽样。研报类长文可以按段落或子标题做细粒度切分。

## Q5：怎么处理中英文混合检索？

数据入库保留 `language` 字段，便于查询过滤和统计。Embedding 用支持中英文的云端模型，语义召回能覆盖双语内容。关键词路径对中文实体、英文公司名、产品名、标题有补充作用。Milvus FULLTEXT 索引同时建在 `title` 和 `content` 上。如果要求更高，可以加中文分词、英文 stemming、跨语言 query rewrite。

## Q6：怎么降低金融场景下的 LLM 幻觉？

三层控制。

第一，检索层提高证据质量——多路召回 + RRF + 时间 / 来源 boost + reranker 提升前几条证据可靠性。

第二，生成层要求答案绑定引用——围绕检索证据回答，缺证据时明确说"没找到"。

第三，Agent 层加入结果评估和自反思——Deep Research 里 Checker 检查证据覆盖、冲突和缺口，必要时触发补检；端到端用 LLM-as-Judge 打 faithfulness / citation coverage 分。

金融场景里 Citation Coverage 是硬指标：每条 claim 必须有 supported citation，否则直接判定不通过。

## Q7：Agent 怎么避免无限循环？

三个限制。

第一，`max_tool_calls=20`，硬上限。

第二，Checker 只对可行动缺口触发补检——比如"缺少某公司某季度财报"；配置类问题（API key 错、外部服务挂）不会进入补检循环。

第三，阶段输入输出结构化，Planner / Retriever / Analyst / Checker / Writer 边界清楚，便于定位是哪一步反复执行。

## Q8：如果 Milvus 查询慢，怎么优化？

先看数据规模、索引类型、`nlist`、`nprobe`、过滤条件和召回 topK。优化方向：

- 调 IVF_FLAT 的 `nlist` 和查询时的 `nprobe`，或换 HNSW。
- 每路召回 topK 调小，靠 RRF 融合。
- 对 `company_id / language / category / published_at` 加过滤缩范围。
- 冷热数据分 collection 或分区。
- 缓存热点 query 的 Embedding 和检索结果。
- 大规模时按业务域拆 Milvus 实例。

## Q9：为什么用云端 Embedding？

服务器 4 核 + 15.6GB，同时跑 FastAPI、Milvus、etcd、MinIO、PostgreSQL 和前端。本地跑 BGE / M3E 会跟其他服务抢资源。云端 Embedding 减本地资源占用，部署更容易。配套工程处理：批处理、重试、超时、错误分级、缓存。成本方面通过 batch_size=50、去重、增量入库和缓存控制。

## Q10：怎么评估金融 RAG 效果？

分检索和生成两层。

检索层不是只看 Precision@5。通用排序指标看 Precision@K / Recall@K / NDCG@K；金融证据指标看 `Source Recall@5`、`Required Source Coverage@5`、`Evidence Hit@5` 和 `Badcase Fix Rate`。比如比较 Apple 和 Microsoft 的收入，系统必须同时召回两份 10-K；数值题还要命中包含年份、单位和数值的 evidence chunk。

生成层用确定性规则 + LLM-as-Judge。确定性规则检查 `Numeric Accuracy`，即数值、单位、期间是否匹配；LLM-as-Judge 辅助打 faithfulness、relevance、correctness；citation coverage 检查 claim 是否有 supported citation。评测集用 FinanceBench 150 条 SEC 财报 QA + LLM 自动生成的金融 QA，按 `query_type` 和 easy / medium / hard 分层统计。`evaluate_retrieval.py` 和 `evaluate_e2e.py` 跑出来后可以接 CI 或定期报告。

## Q11：如果数据规模到 1000 万文章怎么办？

四方向扩展。

- 数据层按时间、语言、来源、业务域做分区和冷热分层。
- 索引层调 Milvus 索引类型、分片、内存、查询参数。
- 检索层先用 `company_id` 等轻量过滤缩范围，再做向量召回 + reranker。
- 工程层加异步导入队列、任务状态表、失败重试、监控告警和缓存。

## Q12：项目最大难点是什么？

三个。

第一，金融多源质量不稳定——财经 RSS 字段格式不统一，飞书需要 token + 限速 + 块解析，SEC 财报是 PDF 派生。采集链路做了"标准化 + 容错 + 去重"，单条失败只记日志，批处理继续。

第二，金融检索既要看语义又得命中实体——单路覆盖不全。三路召回 + RRF 融合，再加时间 / 来源 / reranker，把召回稳定性和前排质量一起优化。

第三，企业级多租户隔离——每条 Milvus 记录带 `company_id`，所有 query 强制过滤，从索引层就保证租户隔离，不是事后过滤。

## Q13：为什么用 JWT，refresh token 怎么管理？

JWT 是无状态认证，FastAPI 容易接，access_token 默认 15 分钟过期。refresh_token 默认 7 天，**只在数据库存 SHA256 哈希，不存原文**。换新 access_token 时比对哈希匹配，匹配才发新 token。这样数据库泄露也拿不到可用 token。`test_production_hardening.py` 里有专门测试覆盖这一点。

## Q14：多租户怎么实现？

每条 Milvus 记录带 `company_id`，每个用户关联一个 `company_id`。所有 query 在 Milvus 检索时强制带 `company_id == X` 过滤。这是从索引层做隔离，不是事后过滤——A 公司的查询永远拿不到 B 公司的数据。配合 quota 管理（每家公司有导入配额），单租户也撑不爆 Milvus。

## Q15：审计日志记什么？

关键操作（查询、导入、研究、配额变更）都记：trace_id、user_id、company_id、操作类型、参数摘要、结果状态、时间戳。结构化存储，生产出问题能回溯到具体用户、具体时间、具体参数。`core/audit.py` 是统一入口。

## Q16：飞书集成最复杂的部分是什么？

`FeishuBlockParser`——把飞书 Docx 返回的结构化 block 数组转成 Markdown。飞书有 30 多种 block 类型（heading1-9 / bullet / ordered / code / quote / todo / table / image / file / mention_user / mention_doc / equation），还要按 `block_id` 父子关系重建表格。Client 侧 token 缓存、限速（Wiki 100/min、Docx 5/s）、3 次重试 + 429 自动退避也是重点。这些都用 36 个专项测试覆盖了。
