# 详细面试讲稿

## 1. 项目开场

RAG Finance Intelligence 是一个面向金融场景的双语 RAG 系统。它把分散在财经 RSS、SEC 财报、飞书企业知识库、Hacker News 和 HuggingFace 金融数据集里的内容沉淀成一个可检索、可追溯、可隔离的证据库，再通过 LangGraph Agent 完成查询分析、混合检索、多源对比、答案生成、来源引用，以及 5 阶段 Deep Research 报告。

这个项目最终输出三种形态：带来源引用的流式问答、长篇 Markdown 研究报告、PPT 大纲。配套的工程能力包括 JWT 认证、多租户数据隔离、企业级配额、审计日志、trace_id 全链路追踪和 GitHub Actions CI。目标是在一台 4 核 / 15.6GB 的服务器上稳定支撑 10 万到 100 万篇金融文档。

## 2. 为什么做这个项目

金融场景跟普通新闻场景相比，有四个独特的痛点。

第一，信息分散且专业。中文有华尔街见闻、财新、第一财经，英文有 CNBC、Bloomberg、FT、WSJ、Yahoo Finance，企业内部还有飞书知识库。不同来源的可信度、更新频率、字段格式都不同。

第二，合规与可追溯要求高。金融答案如果出错代价大，结论必须能回到具体来源、发布时间、URL 和证据原文。我特别在意 Citation Coverage——每条 claim 是否有 supported citation。

第三，多用户隔离。一个 B 端平台要服务多家公司，每家公司的数据、查询、配额、审计都要严格隔离，不能用一份 Milvus collection 把所有租户混在一起。

第四，研究任务长且发散。客户经常问"某只股票最近三个月有哪些重大事件、影响是什么"，这是典型的多跳、多源、长链路问题，需要 Agent 而不是单次 RAG。

## 3. 总体架构

系统分成七层：

```text
企业接入层    JWT 认证 / 多租户 / 配额 / 审计
数据采集层    财经 RSS / FinanceBench / 飞书 / HN / HF Dataset
数据处理层    清洗 / chunk / content_hash 去重 / 元数据标准化
向量存储层    火山引擎 Embedding (dim=1024) / Milvus
检索层       语义 / 关键词 / 标题 三路召回 / RRF (k=60) / 时间衰减 / 来源加权 / CrossEncoder reranker
Agent 层     LangGraph 编排 / 5 阶段 Deep Research
交付层       FastAPI SSE / React + TypeScript + Vite + Tailwind
```

可以这样画：

```text
用户问题 (with JWT)
  -> FastAPI 路由
      -> 鉴权 / 多租户上下文 / 配额检查
      -> LangGraph Agent
          -> 查询分析 (LLM 路由)
          -> 多路召回 (语义 / 关键词 / 标题)
          -> RRF 融合 + boost
          -> 结果评估 + 多源对比
          -> 答案生成 (带引用)
          -> 自反思
      -> 审计日志
  -> SSE 流式回答 + 来源卡片
```

Deep Research 模式会切到 5 阶段流水线：Planner → Retriever → Analyst → Checker → Writer。Checker 发现可行动缺口会回退到 Retriever 补检，最多 20 次工具调用。

## 4. 数据采集与入库

数据层解决"金融资料从哪里来、怎么变成可隔离、可检索的证据"。

### 多源采集

- 财经 RSS：内置 8 个源，CNBC、Bloomberg、FT、WSJ、Yahoo Finance 是英文；华尔街见闻、财新、第一财经是中文，统一标准化为 `title / content / source / language / category / published_at / url / content_hash`。
- Hacker News：技术 + 创业融资新闻，作为补充。
- HuggingFace 数据集：金融领域微调数据集，批量化导入。
- FinanceBench：开源 SEC 财报 QA 评测集（150 条），含 gold answer 和 evidence，用于评测和回灌语料。
- 飞书知识库：自建应用通过 Open API 拉取 Wiki + Docx，token 自动刷新、限速、重试，自动转 Markdown 后入库。

每条记录带上 `feishu_space_id / node_token / obj_token` 等溯源字段，方便在 Milvus 里按租户和来源过滤。

### 入库流程

```text
Collector
  -> 标准化字段
  -> 清洗 (去 HTML / 去 boilerplate)
  -> chunk (RecursiveCharacterTextSplitter, chunk_size=500)
  -> content_hash (SHA256) 去重
  -> 火山引擎 Embedding (batch_size=50, tenacity 3 次重试)
  -> Milvus insert
```

`content_hash` 是去重核心。财经新闻转载率高，标题微调常见，没有 hash 判断 Milvus 集合会快速膨胀。

## 5. Embedding 与 Milvus 设计

Embedding 走火山引擎 API，维度 1024，batch_size 50，tenacity 3 次重试 + 指数退避。

设计取舍：服务器只有 4 核 + 15.6GB，本地跑 BGE / M3E 会跟 Milvus、FastAPI、PostgreSQL 抢资源。云端 Embedding 把 CPU 和内存压力降下来，服务侧只负责批处理、重试和错误处理。

Milvus collection 字段：`id / embedding / title / content / source / language / category / published_at / url / content_hash / parent_doc_id / company_id`。其中 `company_id` 是多租户隔离的关键，向量索引用 IVF_FLAT + COSINE，`nlist=128`。这个参数适配 10 万到 100 万级文章，在召回质量和查询延迟之间取平衡。

如果数据量到千万级，可以拆 collection、冷热分层、加 HNSW 索引、按时间分区。

## 6. 检索方案

金融查询类型混合：有些是趋势归纳（语义召回强），有些是公司名 / 财报期 / 政策名（精确匹配强）。单路检索覆盖不全。

所以采用三路召回 + RRF 融合：

- 语义召回：query embedding + Milvus COSINE 检索。
- 关键词召回：Milvus FULLTEXT，针对 `title` + `content` 全文检索。
- 标题匹配：单独查 title 字段，用于精确新闻标题 / 财报标题。

三路结果用 RRF 融合，参数 `k=60`，权重 `semantic=0.5 / keyword=0.3 / title=0.2`。RRF 对分数尺度不敏感，只看排名位置，工程上稳定。

融合后做时间衰减（半衰期可配，新闻默认 30 天）和来源质量 boost（Bloomberg / FT / 财新 / SEC 权重更高）。前 N 条可以接 CrossEncoder reranker（如 `BAAI/bge-reranker-v2-m3`）做精排。

多租户场景下，每条 Milvus 记录带 `company_id`，检索 query 都加 `company_id == X` 过滤，从索引层就保证数据隔离。

## 7. Agent 工作流

Agent 层用 LangGraph 编排，基础问答链路：查询分析 → 路由决策 → 多路检索 → 结果评估 → 多源对比 → 答案生成 → 自反思。

### Deep Research 5 阶段

```text
Planner      拆解研究目标，输出 3-5 个子问题
Retriever    对每个子问题调多路检索，合并去重
Analyst      从证据归纳趋势、机会、风险、关键判断
Checker      检查覆盖、来源多样性、冲突、时效、缺口
Writer       生成 Markdown 报告、PPT 大纲、最终回答
```

Checker 阶段会做 4 件事：证据覆盖度、来源多样性、新鲜度、缺口和冲突检测。如果发现"可行动缺口"（如缺少某公司某季度财报），会回退到 Retriever 做补充检索；但配置类缺口（API key 错、外部服务挂）会被过滤掉，不会进入补检循环。`max_tool_calls=20` 是硬上限。

### 证据可追溯

每次研究任务都保存 `evidence_trace / execution_log / quality_report / memory_snapshot`。这个对金融场景尤其重要——客户可以复盘结论是怎么来的、用了哪些来源、缺了什么。

## 8. 企业级能力

这是这个项目跟普通 demo 最大的区别。

### JWT 认证

完整流程：注册 → 登录 → access_token + refresh_token → 自动刷新 → 注销。`access_token` 默认 15 分钟，`refresh_token` 默认 7 天，**refresh token 在数据库里只保存 SHA256 哈希**，不保存原文。这样即使数据库泄露，攻击者也拿不到可用 token。`test_production_hardening.py` 里有专门测试覆盖"需要原始 token 哈希匹配才能换新 access_token"。

### 多租户隔离

每条 Milvus 记录带 `company_id`，每个用户关联一个 `company_id`，所有 query 都强制带 `company_id` 过滤。这是从索引层做隔离，不是事后过滤——能保证 A 公司的查询永远不会返回 B 公司的数据。

### 配额管理

每家公司有导入配额（文档条数 / chunk 数 / 存储大小），超过配额时 ingestion 接口会拒绝并返回明确错误。这个在 `cdef731` commit 引入，防止单个租户把 Milvus 撑爆。

### 审计日志

`audit.py` 记录关键操作（查询、导入、研究、配额变更），结构化存储。生产环境出问题能回溯到具体用户、具体时间、具体参数。

### 错误分级

可忽略错误（空检索、单条解析失败）→ 记录 + 继续；关键错误（Milvus 不可用、API key 无效、Postgres 不可用）→ 抛 + 中断。不会因为一个文档解析失败就拖垮整批 ingestion。

## 9. 飞书集成

飞书是企业内部最常见的知识库之一，金融机构的研报、合规文档、内部研究经常存在飞书 Wiki 里。系统接入了完整的飞书 Open API 链路。

### FeishuClient

封装 OAuth 2.0 流程，`tenant_access_token` 自动获取、缓存、提前 5 分钟刷新。HTTP 调用走 httpx 长连接 + 连接复用，自带 429 自动退避（读 `Retry-After`）和 3 次指数退避重试。

### 限速

Wiki API 100 req/min，Docx API 5 req/s，用滑动窗口限速器实现，不会打爆飞书配额。

### 块解析

飞书 Docx 返回的是结构化 block 数组（heading1-9 / text / bullet / ordered / code / quote / todo / divider / image / file / table），FeishuBlockParser 全部转成 Markdown。表格按 `block_id` 父子关系重建行列，公式转 `$...$`，mention 保留为 `@user_id` 或 `[doc_title]`。

### 采集器

`FeishuCollector` 继承 `BaseCollector`，自动注册到 pipeline。逻辑：列出可访问 Wiki → 递归遍历节点 → 过滤 docx 类型 → 拉 blocks → 转 Markdown → 标准化字段入库。每条记录带 `feishu_space_id / node_token / obj_token`，方便审计和回溯。

只有当 `FEISHU_APP_ID` 和 `FEISHU_APP_SECRET` 都配置时才注册——避免空凭据启动时炸。

前端 IngestPanel 下拉也已经加了 Feishu 选项，类型也补齐了。

关键文件：

- `backend/src/ingestion/feishu_client.py`

## 10. 评估与调优

金融 RAG 不能只凭感觉调，所以项目搭了一套完整评测体系。

### 检索评测

`evaluate_retrieval.py` 跑两层指标。第一层是通用排序指标：Precision@K / Recall@K / NDCG@K (K=1/3/5/10)，用于对比纯语义 vs 多路 + RRF vs 加 reranker。第二层是金融证据指标：`Source Recall@5` 看正确文档是否召回，`Required Source Coverage@5` 看比较题需要的多份财报是否都进 top5，`Evidence Hit@5` 看具体证据 chunk 是否命中，`Badcase Fix Rate` 看历史失败是否回归。评测结果还会按 `query_type` 分桶，避免平均分掩盖比较题、数值题和单文档事实题的差异。

### 端到端评测

`evaluate_e2e.py` + 确定性规则 + `LLM-as-Judge`，从 5 个维度打分：

- **Faithfulness**（1-5）：答案是否忠于证据
- **Relevance**（1-5）：答案是否贴合问题
- **Citation Coverage**：每条 claim 是否有 supported citation
- **Correctness**（1-5）：当评测集含 gold_answer 时，对比生成答案和标准答案
- **Numeric Accuracy**：当评测集含 `expected_numbers` 时，检查答案中的数值、单位和期间是否匹配

按难度分层统计：easy / medium / hard 各自的指标，定位系统薄弱处。

### FinanceBench 适配

FinanceBench 是 Patronus AI 发布的 SEC 财报 QA 评测集，150 条开源数据，每条带 `gold_answer` 和 `evidence_texts`。我写了 `seed_financebench.py` 把 evidence_text 当作 chunk 入库，`build_financebench_eval.py` 转成项目统一格式。统一格式里除了 `expected_sources`，还支持 `query_type`、`required_sources`、`expected_evidence`、`expected_numbers` 和 `temporal_constraints`，让评测能从“文档相关”推进到“证据和数值是否正确”。

### LLM 自动生成评测集

`generate_eval_from_milvus.py` 从 Milvus 已有金融文档中按 parent_doc_id 分组，让 LLM 自动生成 QA 对（1 easy + 1 medium），写入 `eval_finance_auto.json`。这个解决了评测集只有 150 条不够用的问题。

## 11. 可观测性与 CI

### Trace

FastAPI middleware 给每个请求生成 UUID `trace_id`，通过 `X-Trace-ID` 头贯穿日志、Agent 执行、下游 LLM 调用。`structlog` 做结构化日志，API key 等敏感字段自动脱敏。

### 错误分级 + 环境保护

空检索、单条解析失败 → 记日志 + 继续；Milvus / Postgres / API key 不可用 → 抛 + 中断。生产环境（`env=prod`）强制关 debug、retrieval_dump 和 LLM cache，防止调试配置带上线。

### CI/CD

GitHub Actions 跑两套测试：

- **frontend**: ESLint → Vite build
- **backend**: pytest 全量套件（133 个测试通过）

## 14. 结尾总结

一句话收尾：

这个项目的核心价值，是把金融数据从"分散、不可信、难追溯"变成"可检索、可隔离、可评估、可审计的证据库"，再用 LangGraph Agent 把检索、分析、校验、生成串成完整流程。技术上我重点解决了金融多源质量不稳定、混合检索召回不稳、Agent 开放任务边界、企业级多租户隔离和金融场景下的可追溯要求这些问题。
