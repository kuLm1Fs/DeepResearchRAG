# 项目亮点与难点卡片

## 卡片 1：金融多源数据质量不稳定

难点：财经 RSS 字段格式不统一，飞书 Wiki 需要 OAuth + 限速 + 块解析，SEC 财报是 PDF 派生，HN 经常只有标题和外链。中文 / 英文 / 企业内部文档混在一起。

方案：统一抽象采集结果为 `title / content / source / language / category / published_at / url / content_hash`。飞书用 `FeishuClient`（token 缓存 + 限速 + 重试）+ `FeishuBlockParser`（30+ block 类型）转 Markdown。HN 优先用 trafilatura 抓外链全文，失败回退到元信息。单条失败只记日志，批处理继续；用 `content_hash` 去重避免转载。

面试表达：金融数据源五花八门，采集链路做成"标准化 + 容错 + 去重 + 溯源字段"的形式，保证单源失败不影响整批，溯源字段也方便审计。

## 卡片 2：金融检索既要语义也要精确

难点：趋势类问题需要语义召回，公司名、产品名、财报期、政策名需要精确匹配。纯语义容易漏实体，纯关键词难覆盖同义表达。

方案：语义、关键词、标题三路召回，用 RRF（k=60，权重 0.5 / 0.3 / 0.2）融合，再加时间衰减、来源质量 boost（Bloomberg / FT / 财新 / SEC 权重高）、可选 CrossEncoder reranker 提升前几条精度。

面试表达：金融查询类型混合，我用多路召回覆盖不同 query 形态，RRF 统一排序，再加时间和来源权重保证前排质量。

## 卡片 3：金融 Agent 开放任务容易失控

难点：研究型任务会不断发现缺口（"缺少某公司某季度财报"），如果补检没边界，执行时间和成本都不可控。金融场景下更要避免 Agent 反复触发"幻觉性补检"。

方案：LangGraph 拆成 Planner / Retriever / Analyst / Checker / Writer。Checker 只对可行动缺口触发补检，配置类缺口（API key 错、外部服务挂）直接过滤。`max_tool_calls=20` 硬上限。每步输入输出结构化。

面试表达：我把 Agent 拆成明确节点，让每步都有输入输出，并用工具调用上限和缺口类型判断控制执行边界，金融场景下尤其重要。

## 卡片 4：金融结论必须可追溯

难点：金融 RAG 答案如果只给最终文本，无法知道结论来自哪些来源、什么时间、什么分数。客户和监管都要审计依据。

方案：保存 `evidence_trace`（每条证据的来源、URL、时间、分数、摘要）、`execution_log`（Agent 每步执行）、`quality_report`（覆盖率、多样性、缺口、冲突）、`memory_snapshot`（研究上下文）。生成层硬性要求每条 claim 必须有 supported citation。

面试表达：金融场景下 Citation Coverage 是硬指标。我的目标是让系统每个核心判断都能回到具体证据、来源、URL、时间、分数，这样答案质量可复盘、可审计。

## 卡片 5：企业级多租户隔离

难点：B 端平台要服务多家公司，每家数据、查询、配额、审计都要严格隔离。一份 Milvus collection 混所有租户会出大问题。

方案：每条 Milvus 记录带 `company_id`，每个用户绑定 `company_id`，所有 query 强制 `company_id == X` 过滤——从索引层做隔离，不是事后过滤。配合 quota（每家导入配额）、审计日志（关键操作结构化记录）、错误分级（关键错误直接中断）。

面试表达：我把多租户隔离从"应用层过滤"下沉到"索引层过滤"，配合配额和审计，让 B 端部署真正可用，而不是 demo 级别。

## 卡片 6：评测体系驱动调优

难点：RAG 项目容易只凭主观体验判断效果，调优没依据。金融场景下没评测更危险。

方案：检索评测分两层，通用排序看 Precision@K / Recall@K / NDCG@K，金融证据看 `Source Recall@5`、`Required Source Coverage@5`、`Evidence Hit@5` 和 badcase 回归。端到端评测用确定性 `Numeric Accuracy` + LLM-as-Judge 的 faithfulness / relevance / citation coverage / correctness。评测集用 FinanceBench 150 条 SEC 财报 QA + LLM 自动生成的金融 QA，按 `query_type` 和 easy / medium / hard 分层统计。`evaluate_retrieval.py` 和 `evaluate_e2e.py` 输出结构化结果。

面试表达：我把评测体系建在项目里，不只看“结果相关”，还看 gold source、required source、evidence chunk 和数值是否命中，用同一套指标比较纯语义 vs 多路 + RRF vs 加 reranker 的效果。

## 五句话总括

1. 我做的是金融领域双语 RAG 系统，覆盖采集、入库、检索、Agent、企业级、CI 全链路。
2. 数据层重点解决金融多源质量不稳定（财经 RSS + 飞书 + SEC + HN + HF），用 `content_hash` 增量去重。
3. 检索层用三路召回 + RRF 融合 + 时间 / 来源 boost + 跨编码器重排，解决金融查询混合问题。
4. Agent 层用 LangGraph 拆节点 + 5 阶段 Deep Research，加 Checker 补检边界和证据追踪。
5. 企业级用 JWT + refresh token 哈希 + 多租户索引层隔离 + 配额 + 审计 + GitHub Actions CI，让系统从 demo 升级到可部署。
