# 工程化改进问题库

这份文件只保留能在面试中体现工程能力的问题。判断标准很硬：必须能讲清楚失败模式、工程取舍、落地方案和验收标准。单纯"接一个高级组件"不算。

## 怎么讲这组问题

不要把它讲成"项目还没做完"。要讲成：

> 这个项目我已经完成了 RAG 主链路、Deep Research、多租户、审计和测试。下一步如果按企业级生产系统推进，我会优先补五个闭环：可观测、任务可靠性、质量评测、压测降级和成本控制。这些不是堆组件，而是为了让系统出了问题能定位、任务能恢复、质量能回归、故障能降级、成本能封顶。

面试里最危险的说法：

- "我上 Prometheus 就企业级了。"
- "我准备用 Celery，所以任务可靠。"
- "我用了 LLM-as-Judge，所以质量可控。"
- "我做压测，支持 100 万文档。"
- "我有限制工具调用次数，所以成本可控。"

这些都会被追问打穿。正确表达必须带指标、边界和验收。

## Issue 1：可观测指标闭环

### 可以怎么说

当前项目已经有 `trace_id`、结构化日志和基础 metrics，但进程内 counter 只能支撑 demo。企业级系统要回答的是"慢在哪里、贵在哪里、错在哪里"。

我会把指标拆成四层：

- API 层：请求量、错误率、p95 / p99 latency。
- 检索层：semantic / keyword / title / graph 各路径耗时和命中数。
- LLM 层：provider、latency、token、估算成本、429 / timeout。
- Agent 层：每个节点耗时、补检次数、unsupported citation rate、research task duration。

### 面试官可能追问

**问：为什么不能直接把 query 或 trace_id 放到 Prometheus label？**

答：这是高基数 label，会把 Prometheus 打爆。trace_id 应该进日志和 trace，不应该做 metrics label。Metrics 只放低基数字段，比如 route、provider、status、stage。

**问：你怎么知道是检索慢还是 LLM 慢？**

答：每个 LangGraph node 都记录 duration，同时 retrieval 内部再拆 semantic、keyword、title、graph 子路径耗时。这样 p95 上升时能定位到具体阶段。

### 最好背下来的句子

> 可观测不是多打日志，而是让系统能回答三个问题：哪里慢、哪里错、哪里贵。

## Issue 2：Deep Research 任务队列化

### 可以怎么说

当前 Deep Research 用 DB 状态和后台 asyncio task 可以支撑 PoC，但生产里不够。worker 重启、滚动部署、多进程、任务重试和取消都会暴露问题。

我已经完成了第三阶段改造：

```text
FastAPI 创建任务
  -> 写 research_tasks
  -> 任务进入 pending
  -> Worker 执行 LangGraph
  -> 阶段性写 progress / heartbeat / result
  -> 失败 retry，超过 max_attempts 进入 dead_letter
```

任务状态机从 `pending -> running -> completed/failed/cancelled/dead_letter` 明确下来，并记录 `attempt_count / max_attempts / locked_by / heartbeat_at / cancel_requested_at / dead_letter_reason`。API 不再在请求进程里直接 `asyncio.create_task` 跑长任务，而是写 durable state，由独立 worker 脚本消费。

这里我没有把可靠性只等同于“上 Celery”。我先把 DB source of truth、worker lease、heartbeat、retry、cancel、dead letter 做成可测试状态机；后续接 Redis broker 时，Redis 负责 wake-up / delayed retry，Postgres 仍负责状态和审计。

### 面试官可能追问

**问：为什么不能只靠 Postgres 表轮询？**

答：Postgres 可以存状态，但不适合承担执行调度语义。队列负责 ack、retry、并发控制和 worker 分发；Postgres 负责状态和审计。两者职责不同。

**问：如果 worker 执行到一半挂了怎么办？**

答：靠 heartbeat 和 stale running 检测。超过阈值的 running task 要么重新入队，要么标记 failed，并保留 failed_step 让用户知道失败在哪。

### 最好背下来的句子

> DB 可以记录任务状态，但不能替代任务队列的执行语义。可靠后台任务要有 ack、retry、heartbeat、timeout 和 dead letter。

> 我这版先把长任务可靠性的状态机落下来了：worker 挂了任务不会消失，失败会有限重试，超过上限进 dead letter，用户取消通过 heartbeat 协作式停止。

## Issue 3：检索质量与 Badcase 回归

### 可以怎么说

RAG 项目最容易假高级：架构很复杂，但质量靠主观感觉。金融场景不能这样，必须把检索质量和答案质量变成可回归的指标。

我会建立三层质量闭环：

- Golden set：FinanceBench + 人工金融查询 + 中文多跳问题。
- Offline eval：Precision@K、Recall@K、NDCG、Source Recall、Required Source Coverage、Evidence Hit、Numeric Accuracy、faithfulness、citation coverage。
- Badcase regression：用户点踩和人工发现的问题进入 badcase，经审核后变成回归集。

每次改 RRF 权重、prompt、reranker，都要比较指标变化。

这个项目里我已经把 eval 从“分类相关性”推进到“金融证据正确性”：统一 `eval.datasets` 加载 JSON / JSONL，FinanceBench 的 `doc_name` 自动映射成 `expected_sources`，同时支持 `query_type`、`required_sources`、`expected_evidence`、`expected_numbers` 和 `temporal_constraints`。`evaluate_retrieval.py` 除了 Precision / Recall / NDCG，还会计算 `Source Recall@5`、`Required Source Coverage@5`、`Evidence Hit@5` 和 `Badcase Fix Rate`；`evaluate_e2e.py` 会额外计算 `Numeric Accuracy`。最终门禁不是看单一分数，而是排序、证据、数值、引用和 badcase 同时达标。

### 面试官可能追问

**问：LLM-as-Judge 准吗？**

答：不能只靠 Judge。检索要有 expected_sources 这种可判定指标；生成可以用 Judge 辅助评估 faithfulness，但必须结合 citation coverage 和人工 badcase。

**问：你怎么证明 reranker 有用？**

答：对比 semantic only、hybrid RRF、hybrid + reranker 三组，在同一 golden set 上看 Precision@5 / NDCG@10 和 badcase 修复率，而不是凭几个样例。

### 最好背下来的句子

> RAG 质量闭环不是跑一次评测脚本，而是每次改检索和 prompt 都能知道有没有退化。

> 对金融 RAG 来说，最关键的检索指标不是分类是否正确，而是 gold source、required source 和 evidence chunk 有没有被召回，所以我把 `expected_sources`、`required_sources` 和 `expected_evidence` 作为离线评测的一等字段。

## Issue 4：外部服务压测与故障注入

### 可以怎么说

这个系统依赖 LLM、embedding、Milvus、Neo4j、PostgreSQL、Feishu。生产里这些外部服务一定会慢、会超时、会 429，所以要压测和故障注入。

我已经完成了第四阶段的工程骨架，重点不是宣称"已经压到 100 万文档没问题"，而是让系统具备可复现的压测和故障降级能力。

现在有三类 Locust 场景：

- 普通 query：看 p95 / p99、检索耗时、LLM 耗时。
- SSE query：看客户端断开、流式中断、生成取消。
- Deep Research enqueue：看长任务入队能力和队列入口延迟。

故障注入通过 `FaultInjector` 做成显式能力，可以用环境变量或 `X-Fault-Injection` header 注入 `graph:timeout`、`llm:timeout`、`milvus:down`、`worker:slow`。`DegradationPolicy` 统一定义哪些故障能降级、哪些必须失败：

- Graph / Neo4j 不可用：hybrid 查询降级到 semantic / keyword / title，并记录 `rag_degradation_events_total`。
- LLM timeout / 429：不让请求无限挂住，短问答走 fail-fast 或 evidence-only，Deep Research 保留已有 evidence。
- Milvus down：这是核心检索依赖，不能假装成功，要明确失败并记录。
- Worker slow / kill：依赖第三阶段的 heartbeat、retry、dead letter 恢复。

另外我加了 capacity report 生成脚本，把 Locust JSON summary 转成报告，自动标出 p95 超预算和错误率超预算的 route。真实面试里我会很诚实地说：工程闭环已经有了，真实容量数字要在目标 4 核 / 15.6GB 机器上跑完报告后才能下结论。

### 面试官可能追问

**问：Neo4j 挂了怎么办？**

答：Graph path 不是硬依赖。hybrid 检索可以降级到 semantic / keyword / title 三路，metrics 里记录 `rag_degradation_events_total{component="graph"}`。用户看到的是证据可能减少，而不是整个问答失败。

**问：LLM timeout 怎么办？**

答：短问答返回结构化错误或降级模型；Deep Research 保留已有 evidence，Writer 可以输出部分报告和缺口说明。不能让一个 provider timeout 拖死 FastAPI event loop。

**问：Milvus 挂了为什么不也降级？**

答：Milvus 是主证据库。Graph 挂了可以少一条检索路径，Milvus 挂了就没有可信证据来源。金融 RAG 不能在没有证据时硬编答案，所以这里应该 fail-fast，而不是伪装成成功。

### 最好背下来的句子

> 压测不是证明系统不会崩，而是找出第一个会崩的地方，并定义它崩了以后系统怎么降级。

> 我不会只说"我做了 Locust 压测"，我会拿出场景、故障注入、p95 / 错误率、降级指标和容量报告，说明第一个瓶颈在哪里。

## Issue 5：LLM 成本预算与熔断

### 可以怎么说

Deep Research 的风险不是单次调用，而是多阶段、多轮补检带来的成本失控。`max_tool_calls` 只能限制次数，不能限制 token 和价格。

我已经完成了第五阶段的第一版成本控制：

- `UsageTracker` 记录每次 LLM 调用的 trace_id、租户、用户、provider、model、operation、prompt tokens、completion tokens 和估算成本。
- `BudgetPolicy` 做请求级 token / cost 预算，可以配置成只 tracking 不 blocking。
- `BudgetedLLM` 包装 LLM client，非流式调用前做预算预检，流式调用边生成边计量，超预算后停止继续消费。
- Agent answer 节点遇到预算耗尽时返回 `[partial report]`，说明基于已有证据输出，哪些还没覆盖。
- `/api/cost/dashboard` 按租户展示请求数、token、估算成本、partial report 次数、按模型和 operation 的分组。

这里的取舍是：第一版先做请求级预算和进程内 usage ledger，足够证明工程闭环；但我不会把它吹成企业账单系统。真实生产还要把 usage 落到 Postgres / ClickHouse，做月度租户预算、价格表版本化、账单导出和告警。

### 面试官可能追问

**问：你怎么估算成本？**

答：LLM client 记录每次 prompt_tokens / completion_tokens，再按 provider/model 的价格表估算。即使不同 provider 返回格式不同，也可以通过 adapter 统一成 usage record。

**问：预算耗尽会不会影响用户体验？**

答：比无限运行或静默失败更好。金融研究报告应该明确说"基于当前预算和证据，只覆盖了 A/B/C，缺少 D/E"。

**问：为什么只限制工具调用次数不够？**

答：一次工具调用可能包含很长上下文，也可能触发昂贵模型。成本边界必须同时限制调用次数、token、金额和执行时间。次数只是其中一个维度。

**问：进程内 usage tracker 有什么问题？**

答：重启会丢，多 worker 会分裂，不能做正式账单。所以它是第五阶段的工程骨架，不是最终计费系统。下一步要落持久化表，并按 company_id 做日 / 月预算和告警。

### 最好背下来的句子

> 对长链路 Agent 来说，成本预算和工具调用上限一样，都是控制系统边界的工程手段。

> 成本控制不是最后看账单，而是在调用前做预算预检、调用中做流式截断、调用后做 usage 归因。

## 面试编排建议

如果只有 1 分钟，不讲这些 issue，讲已有主链路。

如果面试官追问"离生产还有什么差距"，讲前三个：

1. 可观测指标闭环。
2. 任务队列化。
3. 检索质量与 badcase 回归。

如果面试官继续追问"怎么证明稳定"，再讲压测和故障注入。

如果面试官偏 Agent 成本控制，再讲 LLM 预算与熔断。

## 不建议主动讲的点

- 不要主动说"metrics 现在只是进程内 counter"，除非被问到生产差距。
- 不要说"已经企业级生产可用"，应该说"具备企业级雏形，下一步补四个闭环"。
- 不要说"支持 100 万文档已经验证"，除非真的有压测报告。
- 不要说"LLM-as-Judge 保证正确"，它只能辅助发现问题。

泼不出来了。剩下的就是执行的事。
